# Changelog

All notable changes to this project are recorded here. Versions follow
[semantic versioning](https://semver.org/). The version reflects what has
actually shipped, not what would look mature.

## 0.1.0 — 2026-09-06

First release. Everything below was measured on the day it was written; the
commands that reproduce each number are in the README.

### Added

- **Event-time windowing engine** (`src/core/engine.js`). Tumbling windows
  assigned by event time, fired by a watermark, held for a configurable allowed
  lateness, then released. The engine's only notion of processing time is the
  position in the log — no `Date.now`, no `Math.random`, no `setTimeout` anywhere
  under `src/core`, enforced by a test rather than by convention. Replaying a log
  produces byte-identical output including the watermark trace.
- **Five watermark strategies** (`src/core/watermark.js`): `bounded`,
  `bounded-naive`, `percentile` (an adaptive bound taken from observed lateness),
  `punctuated`, and `processing-time`, which is a planted fixture. Each declares
  whether its raw output is monotonic by construction, which is what decides
  whether a falling watermark is a defect or the design.
- **Three late-data policies**, chosen not defaulted: `drop`, `update` (retract
  and re-emit), `side-output`. Events past the allowed lateness are receipted to
  the side output under all three, because there is nothing else honest to do
  with them.
- **Two terminations**: `flush` (the source is exhausted and said so, which
  licenses a final watermark of +infinity) and `idle` (we stopped watching a
  stream that continues, so the trailing windows are genuinely unknown).
- **Batch oracle** (`src/core/oracle.js`): the ground truth every streamed
  result is compared against, sharing exactly one function with the engine.
- **Checker** (`src/core/checker.js`) with three outcomes — `complete`,
  `revised`, `unverifiable` (with a stated reason) — and seven finding codes that
  accuse the engine rather than describe a window.
- **Three vendored real streams** with genuinely different lateness: GH Archive
  GitHub events (max 1.8 min), Wikimedia EventStreams recent changes (max 22 s),
  and the USGS earthquake catalogue (max 15.3 days). Each ships a `SOURCE.md`
  stating the exact URL, what was taken, and its licence position. Only two
  timestamps and a low-cardinality label are vendored per event.
- **Four planted fixtures** (`src/bugs.js`): `processing-time-watermark`,
  `close-without-lateness`, `silent-drop`, and `checker-revised-as-complete` —
  the last of which breaks the checker itself so the `complete`/`revised`
  distinction can be watched to fail.
- **Negative control**: 400 executions of a perfectly ordered, zero-lateness
  stream. Zero revisions, zero unknowns, zero findings.
- **CLI** with `demo`, `run`, `stream`, `check`, `streams`, `fixtures` and
  `bugs`. Bad input produces a stated error and a non-zero exit.
- **Static demo page** (`web/`) plotting event time against processing time with
  the watermark as a line through that plane, so "late" is a region rather than a
  definition. Seed, policy and every other control live in the URL. No server, no
  dataset to download, no credentials.
- **A ~180-line bundler** (`tools/bundle.mjs`) so the page is one classic script
  that loads from `file://`, with a `--check` mode CI uses to catch a stale
  bundle. It refuses module syntax it does not understand rather than guessing.
- **`vendor/MEASURED.json`**, regenerated by `tools/measure-streams.mjs` and
  asserted by the test suite, so every number in the README lives in exactly one
  place.

### Fixed during development

- **124 false positives against a correct engine**, found by running the three
  real streams. `no-pane-after-close` (81) accused the engine of losing windows
  whose events were all receipted to the side output; `unrevised-late` (40) fired
  on every window whose first event arrived after its own close, where one pane
  is the correct answer; `watermark-regression` (3) treated an adaptive bound's
  shrinking sample as a bug. All three are now classified by what they are —
  configuration, not defect. `test/streams.test.js` reconstructs the retired
  conditions and asserts they still total exactly 124, so the claim cannot decay
  into a memory.
- **A true positive silenced by that fix.** `processing-time-watermark` had been
  caught by `no-pane-after-close`, and afterwards produced nothing. Replaced with
  `watermark-overshoot`, an exact structural invariant: a watermark derived from
  observed event times is `maxSeen` minus a non-negative bound and can never rise
  above the highest event time yet seen.
- **A window opened after its own close emitted a "revision" of nothing**, which
  broke the retraction chain. Caught by `pane-chain-broken`. Such a pane is now
  `initial`, and the window carries `openedAfterClose` so the report says the
  watermark overran instead of pretending it did not.
- **The fixture stream was too tidy to break anything.** Event times were laid on
  an exact grid, on which arrival index and event time advance in lockstep and a
  processing-time watermark is accidentally correct. Gaps are now exponential and
  the generator takes a burst.

### Known limitations at 0.1.0

- One process, in-memory state, no checkpointing, no exactly-once across a
  restart, no recovery, no backpressure, no distribution.
- Tumbling windows only; one aggregate (a count).
- The whole log is held in memory; `check` refuses a file over 32 MB.
- The vendored slices are 5,000 events each, not the whole source.
- The Wikimedia slice is a live capture, so re-running `tools/fetch-streams.mjs`
  produces a different, equally valid one.
- CI is committed but has never run: the repository has no remote.
